# 小爪日记：特色玩法与技术规划

日期：2026-09-07。状态：建议方案，尚未实施。

依据：用户提供的截图、当前 package.json、src/main.js、README.md。截图中的家具与功能比本地代码丰富，因此截图仅用作视觉和体验参考，不作为已实现能力的证明。以下按浏览器优先、兼顾手机触屏、单人单宠物的产品范围规划；原生 App、联网社交与商业化另行评估。

## 1. 产品方向

**一句话定位：和一只有自己主意的宠物，把普通的家探索成共同的世界。**

暂定主题“家里有小小冒险”。保留温柔、安静的气质，将辨识度集中在宠物尺度的空间探索、可形成的习惯，以及由实际经历产生的回忆。

当前本地原型的循环是：点击物品 → 走到固定坐标 → 固定时长动作 → 数值增加。自主行为主要由需求阈值与随机散步决定；猫狗共用大部分模型结构与玩法。继续添加家具和数值，较难改变这一体验。

拟调整为：**观察线索 → 改变环境或发出邀请 → 宠物选择和行动 → 发现新路径或事件 → 留下习惯与回忆 → 环境出现下一次机会。**

这里的差异化是待验证的设计主张，不宣称市场上从未有过类似机制。

## 2. 三个相互支撑的特色

### 2.1 房间是可探索的空间

- 阳光随小屋时间移动，温暖区域影响休息地点；不用只靠亮度变化表达昼夜。
- 沙发下面传来小球碰撞声，靠近后才看见线索。
- 一个矮凳可连接地面与窗台；纸箱与隧道能提供遮蔽和穿行路线。
- 允许玩家移动少量指定家具，实际改变通行与互动条件。首版控制为预设摆放槽位，验证后再开放自由编辑。
- 提供近距离宠物跟随镜头；短暂显示听觉方向、气味足迹、可攀爬路径，让玩家理解宠物注意到了什么。

猫偏好高度、狭窄通道和轻物拨弄；狗偏好嗅闻追踪、叼取和拖动。两者可以完成同一段主线，但发现线索与解决问题的动作不同，避免选某种宠物就无法继续。

### 2.2 陪伴会留下习惯

每只宠物拥有少量稳定性格参数，例如好奇、谨慎、亲近、活跃；后天形成的偏好与性格分开保存。

- 连续几次在窗边休息后，它更可能主动去等阳光。
- 喜欢的球会被叼回常待的小角落。
- 第一次靠近新纸箱时先试探，熟悉以后会直接钻进去。

点击仍然有清楚的反馈：接受邀请时看向目标并前往；正在睡觉或动作不能中断时，显示等待或拒绝原因，允许取消等待。不用不受控的随机拒绝制造“性格”。

习惯有形成阈值、每日变化上限和淡化机制；反复刷同一个动作不能瞬间改变性格。需求低时优先自我照顾，长时间未上线不造成死亡或关系惩罚。

### 2.3 日记记录发生过的故事

将“完成喂食”升级为实际事件组合：发现地点、参与物品、宠物动作、首次经历与结果。

例如：“雨天，米粒第一次钻过纸箱，把丢失的小球带回了窗边。”这条文字必须对应真实发生的事件，自动选择一个关键时刻拍照，玩家可以保留或删除。

首版采用规则和文本模板，保证记录准确、离线可用。大模型润色可以后置，且不能生成没有发生过的行为，也不控制实时行动。

## 3. 第一段可验证的玩法

### 小冒险：阳光下的小球

1. 小球滚入矮柜下，宠物被声音吸引。玩家在房间视角看到注意力反馈。
2. 切到近景，发现柜下小球；猫会低伏观察，狗会沿短气味线索嗅闻。
3. 玩家移动挡住侧面出口的纸箱。导航与碰撞更新，通过预览反馈避免把唯一入口堵住。
4. 猫用前爪拨出小球，狗从侧面叼出小球；整个过程必须对齐柜体和球的位置。
5. 宠物把球带到阳光附近。形成一条“首次找回玩具”的回忆，并提高该地点的偏好。
6. 后续到访同一时段，它有机会主动回到这里，玩家能够观察到之前经历留下的影响。

目标单次体验约 5–10 分钟，这是待试玩验证的设计长度。关键验证问题：玩家能否理解环境变化影响行为，以及能否记住自己宠物的偏好。

## 4. 界面与美术辨识度

- 保留截图中的宽阔房间视野，将喂养数值收进可展开的照顾面板。
- 主界面只突出“宠物在关注什么”和一条当前探索线索；减少每日清单对注意力的占用。
- 给原有等距视角增加低机位跟随镜头，探索关键时刻短暂拉近；镜头切换可跳过、可关闭。
- 用宠物高度的叙事道具塑造辨识度：椅脚上的身高刻度、窗台爪印、被藏起来的玩具、纸箱通道。
- 毛色纹理、轮廓与微表情优先于增加多边形；避免通过统一换色区分猫和狗。
- 发现事件奖励新的物品用法、路线与照片收藏。货币用于装饰解锁时，再规划完整经济闭环。

## 5. 当前实现与演进重点

| 领域 | 当前代码                                          | 下一步                                        |
| ---- | ------------------------------------------------- | --------------------------------------------- |
| 工程 | Vite、原生 JavaScript，UI/模型/逻辑集中在 main.js | TypeScript，拆分纯模拟、表现、输入和存档      |
| 3D   | Three.js WebGLRenderer，程序网格与木纹            | 保留渲染器，引入规范化 GLB 资产               |
| 行为 | 需求阈值、随机走动、单一 mode                     | 评分决策 + 可中断动作状态机                   |
| 导航 | 2D 网格 A*、扩大障碍矩形                          | 先完善交互点与布局验证，多层路线引入 NavMesh  |
| 碰撞 | 静态障碍，窝垫专用高度函数                        | Rapier 运动学角色 + 家具碰撞体 + 动作扫掠检查 |
| 动画 | 用正弦函数摆动网格关节                            | 蒙皮骨骼动画、过渡混合、接触事件、脚部修正    |
| 存档 | localStorage，小量固定格式数据                    | 版本化 IndexedDB，迁移、备份导入导出          |
| 日记 | 完成动作后追加固定文案                            | 结构化事件与对应的回忆模板                    |

当前防穿模是原型约束，不能视为已完成可摆家具、多层跳跃场景的可靠碰撞系统。

## 6. 推荐技术栈

| 层级       | 选择                                             | 用途与引入时点                                                             |
| ---------- | ------------------------------------------------ | -------------------------------------------------------------------------- |
| 语言与构建 | TypeScript + Vite                                | 先引入类型、模块边界，保留现有工具链；依赖使用锁文件固定已验证版本         |
| 3D 渲染    | Three.js，WebGLRenderer                          | 复用现有场景能力，第一阶段不迁移渲染后端                                   |
| UI         | 首阶段 TypeScript DOM 组件 + CSS                 | 小体量界面先模块化；复杂编辑器出现后再评估 UI 框架，避免与玩法重构同时迁移 |
| 决策       | 自研轻量评分系统 + 有限状态机                    | 类型化候选动作、条件、超时和取消路径；无需为单宠物引入完整 ECS             |
| 导航       | 初期网格 A*；随后 recast-navigation JS 适配层    | 支持地面与高处平台，off-mesh link 表示可跳跃连接；碰撞不能由导航替代       |
| 物理       | Rapier 3D                                        | 家具碰撞、运动学移动与玩具刚体；先做四足尺寸的单房间验证                   |
| 模型与动作 | Blender → glTF/GLB → GLTFLoader + AnimationMixer | 正式蒙皮模型、动画片段与过渡；控制代码不承担主要造型工作                   |
| 材质       | PBR，KTX2/Basis 纹理，分档资产                   | 压缩传输与显存占用；导出时统一尺度、贴图和色彩空间                         |
| 存储       | IndexedDB + Dexie                                | 宠物、偏好、世界状态、结构化事件、照片；localStorage 只留轻量设置          |
| 音频       | Web Audio API                                    | 用户手势后启用，空间声音表达探索线索；实录短音效替代单一噪声               |
| 测试       | Vitest + Playwright + 真机测量                   | 决策/存档自动测试，浏览器互动与截图测试；真机覆盖热降频和触控              |
| 发布       | 静态构建 + HTTPS + 资源缓存                      | 首版本地单机可玩；PWA 缓存后置，设计资产版本与更新失效机制                 |
| 服务端     | MVP 不需要                                       | 跨设备存档阶段再增加鉴权、存档 API、数据库与照片对象存储                   |

选型理由：当前产品边界是浏览器内小型室内场景，已有 Three.js 原型可复用。视觉品质主要受资产、灯光和动画制作影响，换引擎本身不解决这些问题。如果目标改为以原生商店发行、大量关卡和编辑器工作流为主，再单独做原生游戏引擎验证，不在本阶段承诺跨平台无成本迁移。

## 7. 运行架构与数据流

```text
玩家输入 / 小屋时间 / 感知事件
               ↓
WorldState + PetState（唯一模拟状态）
               ↓
感知 → 候选行为评分 → 动作状态机
                         ↓
               交互点预约 → 路径规划
                         ↓
               运动控制与碰撞修正
                         ↓
               动画、声音、镜头表现
                         ↓
         领域事件 → 偏好更新 / 回忆 / 存档
```

### 模块边界

```text
src/
  app/             初始化、生命周期、依赖装配
  simulation/      时间、宠物需求、世界状态、事件
  behavior/        感知、行为评分、动作状态机
  interaction/     物品能力、交互点、预约和结果提交
  navigation/      网格或 NavMesh 适配、路线更新
  physics/         Rapier 封装、碰撞体和接触查询
  presentation/    Three 场景、动画、相机、声音
  ui/              面板、输入反馈、发现与日记
  persistence/     schema、迁移、存档导入导出
  content/         宠物/家具/发现事件数据
```

模拟逻辑不直接操作 DOM 或 Mesh；表现层读取状态。UI 不直接改变坐标或饱食度，而是提交意图。事件带唯一 ID，奖励和日记对重复事件幂等。

建议初始物理步进 60Hz、普通模拟 10Hz、行为决策 2–5Hz、渲染随帧刷新；这是实现起点，需根据真机成本调优。避免每个渲染帧做完整行为搜索、寻路或 UI 重绘。导航烘焙在需要时放入 Worker，先测量再引入并发复杂度。

## 8. 宠物决策与交互协议

候选行为评分可以由需求、性格、熟悉度、新鲜感、环境舒适度、玩家邀请、距离与风险共同组成。评分前先排除不具备物种能力、路径不可达、交互点被占用或物品已失效的行为。

加入最短驻留时间、切换门槛与冷却，防止宠物在两个目标之间反复转向。玩家请求获得明确反馈；高优先级需求可打断普通散步，但不能突然中断腾空跳跃。

家具需携带：

- 稳定 ID、世界变换、导航轮廓与简化碰撞体。
- 可提供的行为，例如 sniff、eat、climb、crawl、retrieve、rest。
- 接近点、站位、朝向、接触点和退出点。
- 适用宠物体型、动画片段、接触事件和完成条件。
- 移动后的导航失效标记；需要时重规划或取消交互。

动作完整流程：请求 → 校验 → 预约 → 前往 → 对齐 → 执行 → 提交效果 → 离开 → 释放。每一阶段有超时、取消和失败回退。完成时再提交需求变化与奖励，避免宠物还没走到就获得效果。

## 9. 动画、建模与防穿模

### 资产制作约定

每种宠物独立造型和步态，统一米制单位、朝向、原点与命名规范。最低动作集覆盖 idle、walk、turn、sniff、eat、drink、lie-down、sleep、wake、play、pet-reaction，猫狗分别增加 crawl/paw 与 carry/retrieve。

模型交付包括 .blend 源文件、GLB、贴图、碰撞代理、动画片段清单及接触事件配置。猫狗可以共享控制接口，不强求共用骨架。需要预留美术制作或授权采购工作量；资源授权要覆盖修改和随游戏分发。

### 动画落地

- 用真实位移速度驱动步态速度，设置短时交叉混合，先消除滑步和瞬间转身。
- 低成本头部注视、眨眼、耳尾动作增加生命感；关键近景再做脚部接触修正。
- 移动主体由运动控制器拥有位置；原地动画跟随移动。特殊动作的根运动增量也需经过碰撞检查，不能同时让动画和控制器修改同一世界坐标。
- 叼球在接触帧绑定嘴部挂点，放下时恢复刚体；进食在正确接触帧触发效果。

### 防穿模分层

1. 布局层：验证入口、宠物净空和重要物品可达性。
2. 导航层：按宠物体型烘焙或膨胀障碍，窄缝不错误通行。
3. 运动层：运动学碰撞修正，实际位置反馈给寻路和动画。
4. 互动层：到位后校验朝向、站位、接触点；失效则重规划。
5. 跳跃层：off-mesh link 只表示连接。起跳前校验落点和扫掠轨迹，落地后重新接入导航。

Rapier 的通用角色控制器是起点，不能自动解决四足身长、尾巴与家具、身体进入狭窄空间的问题。先验证简化躯干形状与旋转净空，装饰性尾巴通过姿态约束规避；不承诺绝对零穿模。

## 10. 移动端性能预算与存档

以下是验收目标，不是目前测量结果。开发时锁定一台 Android 中端机和一台 iPhone，并记录机型、系统和浏览器版本。

| 指标                   | 初始目标                                                        |
| ---------------------- | --------------------------------------------------------------- |
| Android 中端机持续运行 | 中画质 30fps，连续 10 分钟记录 P95 帧时与热降频                 |
| 桌面                   | 目标 60fps，测量 CPU/GPU 时间并定位瓶颈                         |
| 首屏必要资源           | 压缩传输预算 8MB 内，20Mbps/100ms RTT 冷缓存下争取 5 秒内可操作 |
| 默认可见三角形         | 约 15–25 万起步，按实际 GPU 测试调整                            |
| Draw call              | 默认视角先控制在约 120 以内                                     |
| 阴影                   | 移动低档单灯 1024；更高档按实测开启 2048                        |
| 材质                   | 物件优先 512/1K，主角按画面占比使用 1K/2K，开启 mipmap 与压缩   |
| 触控                   | 操作区至少约 44 CSS px；区分点击、拖拽、双指缩放与手势取消      |

高、中、低档分别控制像素比、阴影、后处理与装饰密度；不降低行为逻辑正确性。避免以所有资源使用 4K 贴图作为“高清”标准。

存档需保存 schemaVersion、宠物、偏好、世界布局、发现事件和小屋时间。导入时校验，迁移失败保留原始备份；相片与模拟状态分开存储并提供删除和导出。浏览器数据可能被清理，不能把本地保存表述成永久保存。

离线只计算有上限的时间变化，不重放逐帧物理，不补造玩家不在时的具体冒险照片。将“离线推算”与“实际观察到的事件”区分记录。未来云存档必须增加版本与冲突策略，不能直接互相覆盖整个对象。

## 11. 迭代与验收

以 1 名前端/游戏工程师 + 1 名能制作模型和绑定动画的美术为假设，以下为粗略排期，不是交付承诺；资产复杂度和真机测试会显著影响工期。

| 阶段                  | 参考工作量                   | 可验收结果                                                       |
| --------------------- | ---------------------------- | ---------------------------------------------------------------- |
| A：工程与行为拆分     | 3–5 工作日                   | TypeScript 模块化；原玩法与旧存档迁移通过；行为切换无振荡        |
| B：特色切片           | 5–8 工作日                   | 一个房间、一段找球事件、两种不同解法；原型模型也能让玩家理解特色 |
| C：正式宠物与接触动作 | 8–15 工作日，可与 B 部分并行 | 猫狗独立资产、步态过渡、叼球/拨球、至少一个登高或穿行交互        |
| D：习惯、回忆与移动端 | 5–8 工作日                   | 偏好可形成和复现、事件日记、迁移和真机性能报告                   |

阶段工作量不能简单相加得到日历工期。单人同时负责代码与美术时应缩减内容，并重新估算。

关键验证：

- 找 5–8 名试玩家，不解释设计，观察能否在首段体验中理解并完成发现事件。
- 改变家具布局后，宠物路线或发现方式确实改变；堵路时有明确反馈。
- 相同性格、状态和随机种子可以复现决策；不同偏好在多轮观察中产生可见差异。
- 通过真实事件形成一个地点习惯，刷新后继续可见。
- 动作取消、移动家具、后台恢复、保存损坏、更新升级均有回退路径。
- 对每种体型和每个交互点运行多起点路径测试；记录碰撞与卡住位置，修复可重复问题。

首个优先交付物是阶段 B 的“阳光下的小球”体验，同时完成其必需的 A 阶段拆分。美术和系统扩张应由这段体验的试玩结果决定。
